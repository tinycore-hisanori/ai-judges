AI Judges — App Map

A take-home guide to where things live. Snapshot of commit 5e39ccd; the code can drift after this.

What it is

A single web page where three AI judges — an engineer, a marketer and an investor — each give a 3–5 line hackathon pitch a score, a one-sentence reason and one fix. You rewrite, resubmit, and see each score move. Every judge is a prompt to a local model in Ollama, so pitches never leave the machine. No build step, no server code: plain HTML, CSS and ES modules.

index.html + style.css

The stage: header, language toggle, the three cards, the pitch box and the total badge.

judges.js

Who the judges are: MODEL, the shared rules, each persona prompt and seed, and buildMessages.

app.js

Everything that happens: running a round, the one model call, checking answers, rendering, saving, UI strings.

Ollama (local)

POST http://localhost:11434/api/chat with a JSON schema, temperature 0.2, a fixed seed per judge and num_ctx: 6144.

One action: “Submit to the panel”

Reference route (3 stops)

A route for finding your way back in, not a record of a guided tour. Search for the symbol in your editor; line numbers are approximate.

  1. submitRound() in app.js (~line 187)

    Moves each judge's last verdict into state.previous, sets the cards to “Reading…”, then awaits runJudge for each judge in turn. finishRound() shows the all-fail banner, counts the badge up and calls save().

  2. SHARED_RULES, JUDGES and buildMessages() in judges.js

    The judging behaviour is all prompt: the rubric bands, the evidence → band → reason → score → fix order, and each persona's priority. buildMessages sends the persona prompt, then (on a resubmit) only “For reference, last round you gave N.”, then the pitch, cut to 6,000 characters.

  3. callJudge() → askJudge() → validateVerdict() in app.js

    callJudge is the only place that talks to the model. validateVerdict rejects a score outside 0–100, an empty reason or fix, an empty quote and a fix over 300 characters; askJudge then retries once with seed + 1. Network or timeout errors skip the retry and show “The judge left the room”.

    The checks, as written 
    if (!Number.isInteger(v.score) || v.score < 0 || v.score > 100) fail("score out of range");
if (typeof v.reason !== "string" || !v.reason.trim()) fail("empty reason");
if (/["“「]\s*["”」]/.test(v.reason)) fail("empty quote in reason");
if (typeof v.fix !== "string" || !v.fix.trim()) fail("empty fix");
if (v.fix.trim().length > MAX_FIX_CHARS) fail("fix is a rewrite, not one change");

A practice to reuse

Keep the kernel demo as a re-runnable check, and run it after every late addition.

The kernel here is “the same panel changes its mind when the pitch improves”, captured as one three-round story (30 → 48 → 75, Would advance). During final review, a one-line prompt addition (“Answer in the language of the pitch”) looked harmless, but rerunning the story showed round 3 dropping to 67 because the engineer's verdict was borderline. Placing the line elsewhere didn't help, and rewording the pitch only moved the problem to another judge. So the line was cut and the language behaviour kept as the model's default (see devpost/checklist.md › Revisions).

On another project: write the kernel's demo down as concrete inputs and the expected visible result, script it, and treat “the demo still ends the same way” as the gate for anything added after the core works. When an extra and the kernel conflict, cut or weaken the extra.
